# Threat model

STRIDE-lite: an asset, the way in, the threat, the control that answers it and what's left over. The long form of each control is in `docs/06-security-and-governance.md`, section 2; the pipeline steps referenced are in `docs/02-architecture.md`, section 4. Fourteen rows, then the logging policy in five lines, then what the model leaves out. The pull request that will pin each control is named in its row.

The people in it. A member of the public who writes an instruction into an answer, or ten thousand of them behind a campaign. A policy team member who uploads a crafted file, or just a very big one. A department user reaching for another department's data. An operator with the admin console. Whoever holds a leaked gateway token. Trust boundaries, with what crosses each:

| Boundary | Trusted side | Untrusted side | What crosses it |
|---|---|---|---|
| The upload | The `stage` job and the validator | The browser and the file | The file, by presigned URL; only its header row is read in a request |
| The prompt | The worker's prompt prefix | The public's answers | JSON-encoded answers after the preamble; the model's structured reply on the way back |
| The department | Every query with its scope | Every other department | Nothing, if the scope holds |
| The gateway | The worker, holding one token | The provider behind the alias | Prompts out, completions back; the region recorded per job |

## 1. Assets, entry points, threats, controls

| # | Asset | Entry point | Threat | Control | Residual risk |
|---|---|---|---|---|---|
| 1 | The uploaded file, with identity columns | Presigned multipart upload from the browser (step 1); parsed inside the `stage` job (step 2) | Denial of service and tampering: an XLSX is a zip of XML, so one file can be a zip bomb and an entity-expansion attack; a file that isn't what its extension says | Size cap on the presigned URL and again at stage; decompression-ratio ceiling before the zip is opened; `defusedxml`; CSV row and cell length caps; parsing in a job, never in a request; sha256 recorded. PR-04 will pin the guards | A large legitimate file hits a cap and has to be split. The caps are settings, and the first real upload will say whether they're right |
| 2 | The prompt | Public text in open answers, sent in batches of ten (step 9) or about fifty (step 6) | Prompt injection: an answer telling the model to tag every response with one theme, to emit extra ids, or to rewrite the theme list | No tools; answers as JSON-encoded data after a preamble that says instructions inside them are data; enum labels; two-way id check; ten per batch; retry at size one; `unprocessable` bucket. PR-07 will pin the prompt contract | Nothing here stops an injection; the controls bound what one can do, which is where NCSC says to put the effort (`docs/01`, section 3). A persuasive answer can still mis-tag itself and its nine neighbours, and the reviewer's edits are how it shows |
| 3 | Model output | The gateway's response | Tampering with structure: ids missing, ids added, a label outside the enum, malformed JSON | Structured outputs plus schema validation in code; the enum; the two-way check; a bad batch rejected whole and retried at size one | A well-formed wrong answer passes every check. The edit stream from sign-off and per-tag corrections is the only measure of that |
| 4 | The queue | Any principal with `SendMessage` on the SQS queue | Spoofing and replay: a forged or replayed message naming a job id | The message is a hint. The conditional claim (step 5) refuses anything the `job` table doesn't say is `queued` or stale; IAM lets only the reconciler's role send. PR-05 will pin the claim | A replayed message for a stale lease triggers a takeover slightly early. Harmless: the fence holds |
| 5 | The database: answers, tags, `attrs`, versions | The web app and worker roles; a query path that forgot its scope | Information disclosure across departments; elevation through SQL injection in a filter; tampering with tags or a signed-off version | `department_id` on every table with a mandatory scope; parameterised SQL only (PR-09 will hand the query builders hostile filter values); versions immutable; tags retracted with an `audit_event`, never deleted except by an erasure (`docs/06`, section 4); row-level security as the escape hatch | Scoping in code can be missed on one path and nobody notices until two departments share a screen. That's why the escape hatch exists |
| 6 | The identity vault | The ingest role at step 3a; the export role at step 12 | Disclosure: identity joined back to answers by the pipeline; an email address in a prompt | The pipeline role has no grant on the `vault` schema; `attrs` isn't on the prompt path; regex masking on the prompt copy of an answer. PR-03 will create the roles; PR-06 will connect as the pipeline role and expect a permission error | A respondent who writes their own name into an open answer sends it to the model unless the regex catches it. NER is on the cut list, and `docs/06` section 6 says why |
| 7 | The exports | The `export` job; a presigned download link | Tampering: formula injection when the XLSX opens in Excel; disclosure through a forwarded link; a stale export after an erasure | Text cells only, with a neutralising prefix on formula trigger characters (PR-09 will pin it); links that live for minutes; exports regenerated after erasure and the old objects removed | A downloaded copy is outside the service. Recall is the department's, as controller |
| 8 | The emails | The outbox relay to GOV.UK Notify | Disclosure: response text or a theme in an email; spoofing: a link to the wrong consultation | Name, status and a link, nothing else (ADR-006); the link opens the app, which applies scoping; Notify keeps content seven days (`docs/01`, section 3) | One duplicate email inside the stated window. A nuisance |
| 9 | Logs and traces | CloudWatch, Sentry, Langfuse | Disclosure: answer text in a log line or a stack trace; `job.error` carrying a provider message body that echoes the prompt | Ids, counts, durations and error codes only; Sentry with `send_default_pii=False` and a scrubber; `job.error` a code plus a request id; Langfuse holds text by design, inside the boundary, platform team only, retention aligned. PR-03 will pin `job.error` and the formatter | A new log line by a future engineer. PR-03's test will cover `job.error` and the formatter, and nothing stops a stray `print` |
| 10 | The operator console | Django admin over `job`, `question`, `notification_outbox`, `department` | Elevation and repudiation: an operator retries a job in a paused department, reassigns a question, resends an email, and later denies it | Every action writes an `audit_event` with actor, before and after; the console can't edit a version or a tag; pause and budget are data the dispatcher reads | An operator is trusted. The audit trail is the control after the fact, and the section 2 logging policy is what keeps it from also being a leak |
| 11 | The gateway token and other secrets | The worker's environment at task start | Disclosure: a token in the image, in git, in a log line | Model keys stay in the gateway; one token per environment from a secrets manager, injected at task start; the gateway's spend cap; the department budget | A leaked token spends up to the cap until it's rotated. Rotation is a runbook line and the cap is the bound |
| 12 | The consultation configuration | The configure screen (step 3) | Tampering by mistake: an identity column marked demographic, so an email address lands in `attrs` and on the dashboard | Defaults by header name; the validator lists distinct values per demographic column with counts (`docs/02`, section 3.2), so an identity column shows as thousands of unique values; check-your-answers before Confirm | A determined misconfiguration goes through. Erasure and retention still work on the result |
| 13 | The signed-off theme list | The sign-off screen (step 8) | Repudiation: "I never confirmed that list"; tampering: two reviewers editing at once | The guarded `UPDATE` as the mutex; the version guard on every edit; an `audit_event` with user and time; immutable versions. PR-05 will pin the guard | Nothing to speak of on the mechanism. A reviewer who confirms everything as-is is a product risk, and ADR-003 says how it's made visible |
| 14 | The pipeline's capacity and budget | Upload and Confirm; a bot campaign of 90,000 rows | Denial of service and wallet drain: one consultation starves every other department; a campaign costed and analysed as if it were 90,000 people | Caps of 6 per department, 4 per consultation, 20 service-wide with round-robin (step 4); a monthly budget with pause; the cost estimate on the Confirm screen; duplicate flags at both levels | A bot campaign gets analysed unless someone reads the validator's duplicate counts. The 90,835 of 118,756 in `docs/01`, section 5, is the case to remember |

The STRIDE letters, and where each lands: spoofing in rows 4 and 8; tampering in 1, 3, 5, 7, 12 and 13; repudiation in 10 and 13; information disclosure in 5, 6, 7, 8, 9 and 11; denial of service in 1 and 14; elevation of privilege in 5 and 10. Row 2 is the one STRIDE doesn't name well: an injection that changes what the model does is tampering with the output by way of the input, and the control is that the model has no tools and an enum to answer in, so there's little to gain by trying.

## 2. Logging policy

1. At INFO on the worker and the web app, with ERROR the level CloudWatch alarms on (docs/02, section 3): consultation, question, job, batch and run ids; row, answer, token and tag counts; durations; the state before and after a transition; the error code on failure. Every line carries the correlation ids.
2. Never, at any level: an open answer, a demographic value, a theme label, a prompt, a completion, an email address, a filename from the upload, or a provider error message body.
3. `job.error_code` holds an error code from a fixed vocabulary and `job.provider_request_id` the provider's request id (docs/04); there's no column for a message body. A person debugging goes from the request id to the trace, never from the log to the text.
4. Langfuse traces hold the prompt and the completion for every call, by design, on the gateway side inside the OFFICIAL boundary, with retention aligned to the consultation's `retention_until`. The platform team can read them. Department users and operators can't.
5. PR-03 will pin lines 1 to 3 with a test on the log formatter and on `job.error`. Line 4 is an assurance the platform team gives, and ADR-005 says what happens if they can't.

## 3. What this model does not cover

- Authentication, sessions and device security. Upstream, per `docs/02`, section 1.
- An insider with database credentials or the platform team reading traces. Encryption at rest doesn't stop them; access logging at the RDS and gateway level is a platform question, and `docs/06`, section 2.8 names the gap.
- The gateway's internals and the model provider's handling of prompts. The design records the region per job and names the provider's terms in the DPIA pack; it doesn't model them.
- Network controls: VPC layout, security groups, TLS configuration. Assumed, and described in Terraform rather than argued here.
- Whether a response is genuine. Duplicates are flagged and counted both ways; who sent them is the department's judgement.
- Supply chain. PR-03 will run `pip-audit` and `bandit` in CI on the proof-of-concept, which is a start and not a model.
- Anything the proof-of-concept doesn't reach: the web app, the dashboard and the exports exist here as design, and the rows above that name them are about the design.

## 4. What I'd check first in a review

1. A new query path without the department scope. Read every `SELECT` that a request can reach and look for the one that takes an id from the URL and nothing else.
2. The prompt contract. Diff the prompt against the list in `docs/06`, section 2.2, and look for anything from `attrs` or the vault.
3. The log formatter. Grep the worker for anything logged that came from a spreadsheet cell.
4. The vault grants in `schema.sql`. One `GRANT SELECT` to the pipeline role undoes row 6.
5. The export writer. Put `=1+1` in an answer on the fixtures and open the result.
